section verifies the whole path from browser to model.

\vspace{0.5em}\noindent\textbf{Step 2. Verify recommendations are actually
personalised}\par

This is the single most important check in the system. Call it with two
different users:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{curl} \StringTok{"https://.../recommendations?userId=user{-}001"}
\ExtensionTok{curl} \StringTok{"https://.../recommendations?userId=user{-}150"}
\end{Highlighting}
\end{Shaded}

The two results \textbf{must differ}. If they are identical, the model
is not personalising and is only returning a general popularity list.

\vspace{0.5em}\noindent\textbf{Step 3. Verify recommendation order is
preserved}\par

This is a subtle bug that produces no error message at all.

Personalize returns a ranked list. Lambda then queries DynamoDB to fetch
full details for each product. The catch: \textbf{DynamoDB does not
guarantee results come back in the order the keys were passed in}.

If the code does not re-sort, the ranking the model computed is lost,
and the best-matching product can end up at the bottom of the list.

How to check: compare the order of \texttt{itemId} values from
\texttt{get-recommendations} with the order of products returned by the
API. They must match.

\vspace{0.5em}\noindent\textbf{Step 5. Test order price
security}\par

The server must recalculate totals itself rather than trusting the
browser. Try submitting an order with a tampered price:

\begin{Shaded}
\begin{Highlighting}[]

The created order must carry the \textbf{real price} from DynamoDB, not
the price of 1 that was submitted. If the order records a price of 1,
you have a serious vulnerability.
